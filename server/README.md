# La Familia server

Laravel 13 (PHP 8.5) with a Filament 5 admin panel, on FrankenPHP with MySQL 9.7 and Redis 8
(cache, sessions and queues). PHP, the queue worker, the scheduler, MySQL and Redis all run under
Podman.

## Run locally

First run:

```
cd server
podman machine start                    # if it is not already running
cp .env.example .env
podman compose up -d --build            # the first build takes several minutes
podman compose exec server composer install
podman compose exec server php artisan key:generate
podman compose exec server php artisan migrate --seed
podman compose exec server php artisan storage:link
podman compose exec server php artisan app:create-admin
npm install --ignore-scripts && npm run build
```

After that, `podman compose up -d` starts everything.

| URL                         | What        |
|-----------------------------|-------------|
| http://localhost:8001       | Application |
| http://localhost:8001/admin | Admin panel |

The source is bind-mounted, so PHP changes apply on the next request. Node stays on the host:
use `npm run dev` for hot reload.

Host ports are offset from the defaults so this stack can run alongside other local projects:
the app is on 8001, MySQL on 3307 and Redis on 6380. `.env` holds those published ports for
host-side tools such as the Laravel Boost MCP server, and `compose.yaml` overrides them for the
containers. For that reason, do not run `php artisan config:cache` on the host: the bind mount
would hand the host's settings to the containers.

## Language

The interface is in Spanish (`APP_LOCALE=es`); code, tables and columns stay in English. Framework
strings live in `lang/es`, generated by `laravel-lang` (`php artisan lang:update` refreshes them).
App strings also live in `lang/es`, for example `lang/es/settings.php`.

## Settings

The `settings` table holds values by key (`company_name`), edited at `/admin/settings`. The panel
changes values only. To add a setting, add it to `Database\Seeders\SettingSeeder` and its Spanish
name to `lang/es/settings.php`, then run `php artisan db:seed`. Existing values are kept.

`company_name` is the panel's brand name; `APP_NAME` is the fallback when it is empty. Read a
setting with `Setting::valueOf('company_name')`.

The application timezone is `America/Mexico_City`, and timestamps are stored in that timezone.

## Users and roles

Each user has one role, chosen at creation and final after that. Roles are the `App\Enums\Role`
enum: add a case and its Spanish label in `lang/es/users.php` to create one.

Every service lists its allowed roles in code, through the `role` middleware:

```php
protected static string|array $routeMiddleware = 'role:cashier,driver'; // Filament resource
Route::post('sales', SaleController::class)->middleware('role:cashier');  // any other route
```

Admins pass every check. To exclude them, declare it: `role:exclusive,driver`. New Filament resources
extend `RoleGuardedResource`, which reuses the same list to hide what a user cannot open. For other
interface elements use `auth()->user()->canActAs(Role::Cashier)`.

Users sign in once and work across their assigned branches. A non-admin needs at least one assigned
branch to sign in. Admins skip branch checks and can work in any branch. They are still assigned to
every branch automatically, both when a branch is created and when an admin is created, so `forBranch`
lists them. Add `branch.access` to a route to reject requests for a `{branch}` or
`branch_id` the user is not assigned to. `BelongsToBranch` refuses the same at model level.

Create the first admin with `php artisan app:create-admin`. `make:filament-user` does not work here
because it cannot set a role.

## Products

`products` is the shared catalog, with an optional unique `barcode` and a picture stored on the
`public` disk as `products/{id}.{extension}`. Each branch has its own Productos section, backed by
the `BranchProduct` model on the `branch_product` table, which holds that branch's unit and price.

There is one row per product and branch, even across soft deletes. Add a product to a branch through
`BranchProduct::addToCurrentBranch()`, which restores a removed row instead of hitting the unique index.

Barcode scanners type like a keyboard and finish with Enter. The barcode field ignores that Enter,
product pickers and tables search by barcode, and `Product::findByBarcode()` reads a scan.

## Inventory

Stock is never calculated by summing movements. `inventory_movements` is an append-only ledger, and
`branch_product.stock` holds the current balance. `App\Services\Inventory` is the only writer of
both, updating them in one transaction under a row lock.

```php
app(Inventory::class)->record($branchProduct, MovementType::Sale, '2.5', reference: $sale);
```

- Movements are never edited or deleted. Correct a mistake with a new adjustment. That makes this the
  one business table without soft deletes or entity logs: each row already says who did what.
- Quantities are decimal strings, handled with bcmath, never floats.
- A sale is allowed without enough stock. It is flagged, and it notifies admins and that branch's
  managers. Adjustments in the Inventario section can take stock below zero on purpose.
- A product's unit in a branch is final from creation. Re-adding a removed product keeps its unit and
  its stock.
- `inventory:reconcile` runs nightly in the `scheduler` container and logs an error if any balance
  disagrees with the ledger.

## Notifications

Laravel's `notifications` table, related to users, feeds the bell in the panel. To send mail through
Resend, follow the comments in `.env.example`; otherwise it goes to the log. Notifications run on the
queue, after the database commit, so a mail failure cannot undo a sale.

After changing `.env`, run `podman compose restart queue scheduler`. The worker keeps the values it
started with, so without a restart jobs run with old settings, such as the wrong language or mailer.

## Soft deletes and entity logs

Every business table has `deleted_at`, and changes to its rows are recorded in `activity_log`
with who made them (`spatie/laravel-activitylog`). Add both to a new table with
`$table->softDeletes()` in the migration and `use Auditable` on the model;
`tests/Feature/Models/Concerns/AuditableTest.php` fails if either is missing. Framework tables
such as `jobs` and `sessions` are listed as exceptions in that test.

Each entity row has a menu icon with its options, including a history entry that opens its log. For a
new resource, add a `ViewRecord` page as `view`, extend `EntityHistory` as `history`, and put the row
actions in one `ActionGroup`, including `ViewAction` and `HistoryAction`.

Only changes made through a model are logged. Query builder updates such as
`Branch::query()->update(...)` are not, and hidden attributes such as passwords never are.

## Branches

The app is organized around branches. The sidebar lists entities that exist on their own (settings,
branches) first. Below a separator comes the branch selector and the modules of the selected branch.
The selection is kept in the session by `App\Support\CurrentBranch`, which offers the branches the
user can work in: their assigned ones, or all of them for admins. A user with a single branch never sees the selector or the branch name.

| Records                                       | Model trait        | Stored in                 |
|-----------------------------------------------|--------------------|---------------------------|
| Owned by one branch (delivery routes)         | `BelongsToBranch`  | `branch_id` column        |
| Assigned to several branches (users)          | `AssignedToBranch` | `branchables` pivot table |

Both traits add `forBranch($branch)`, so queries read the same either way. To add a branch module,
use one of the traits on the model and `ScopedToCurrentBranch` on the Filament resource. That limits
every query to the current branch and moves the resource below the selector.

## Useful commands

```
podman compose exec server php artisan test     # uses in-memory SQLite (see phpunit.xml)
podman compose exec server composer require ...
podman compose exec server vendor/bin/pint      # format code
podman compose logs -f server queue
podman compose down                             # stop, keeping data
podman compose down -v                          # stop and wipe all data
```
